# Claude 전달 — Go2 상태별 성능 분석·표 작성·튜닝 정책 도출

작성: Codex, 2026-10-01. 사용자 요청에 따른 분석 지시서다. 새 학습·서버 실행·패키지 발행 지시가 아니다.

## 0. 목적과 현재 위치
- 목표: 계단(G5), 험지(G3), 복합 우회전(G2), 밀침(G6)에서 **어떤 상태의 로봇이 생존과 명령 추종을 함께 잘하는지**, 높이는 낮을수록/높을수록 유리한지 또는 유망 구간이 있는지 찾는다. 그 결과를 기존 보상 변경 이력과 연결해 실행 가능한 튜닝 정책으로 정리한다.
- 단계: 2/6, 기존 실험 결과로 다음 튜닝 판단. 현재 증거로 공식 성능을 판정하지 않는다.
- 확보: 서버 여러 단일변수 실험, PC A048 재학습, 원 steps/summary와 일부 발·관절 진단 자료. 기존 몸높이 비교 49개 arm×case, 4,704개 env 기록.
- 미확보: 몸높이의 독립 인과효과, 상황별 최적 높이, 서버/PC 환경 차이의 분해. 불확실성은 분석 중단 이유가 아니라 결론 범위다.
- 사용자 할 일: 없음. Claude가 로컬 자료로 분석·표·정책안을 작성해 Codex에 전달한다.
- 흐름: 기존 결과 → 상태·성과 비교 → 유망 상태와 반례 → 보상 변경 대응 → 정책 선정 → 별도 요청 때만 실행 패키지.
- 보장하지 않음: 관측 최선점은 검증된 최적 제어 목표나 보상 최적값이 아니다.

## 1. 사용자가 원하는 답
1. 각 상황에서 몸높이를 비롯한 상태가 어느 방향으로 변할 때 결과가 좋아지는가?
2. 최선의 관측점과 유망 구간은 얼마인가? 어디까지 실제 자료가 뒷받침하는가?
3. 하나의 고정 자세가 아니라 상황별 자세 전환이 필요한가?
4. 이미 시험한 어떤 보상 변경이 그 상태를 실제로 만들었으며, 다른 상황에서는 무엇을 잃었는가?
5. 이 근거로 다음 보상 방향·값·기준 설정을 선택할 수 있는가? 선택한다면 반례와 설계 이유까지 제시한다.

단순히 '상관일 뿐', '낮다고 무조건 좋지 않다', '추가 연구 필요'로 끝내지 않는다. 비교 가능한 범위에서 우선순위와 유망 상태를 좁힌다. 반대로 숫자를 요구받았다는 이유로 표본 없는 최적 구간을 만들지 않는다.

## 3. 지금까지의 결과 — 반드시 새 표와 대조
높이(m)는 root_z − 높이 스캐너 영역의 평균 지형 높이다. 몸 바로 아래 지면 거리·발 여유 높이·관절 굽힘 각도가 아니다.

초기 높이는 첫 종료 전 1~3초에서 1초 이후 첫 upright!=1 직전까지, 최소 25행을 확보한 로봇별 시간 중앙값의 중앙값이다. 정상 보행 보증이 아니며 정지 로봇도 들어갈 수 있다. 전체 summary 중앙값과 혼용하지 않는다.

| A033 | .365 | 59 | .339 | 0 | 90 |
| A043 | .356 | 24 | .324 | 77 | 49 |
| A044 | .352 | 80 | .332 | 0 | 95 |

동일 정책 안의 15cm 모서리 직전 높이(직전 25행 upright=1 표본만):
- A043 미도달 .308m/18대, 도달 .310m/68대.
- 서버 A048 미도달 .271m/61대, 도달 .281m/22대.
- PC A048 미도달 .318m/87대, 도달 .329m/6대.

**Codex의 직전 제안은 '험지 약 .24m, 계단 접근 약 .31m'였다. 이 숫자는 검증할 관측 후보점이지 확정 최적값이 아니다.** 특히 .24는 초기 구간, .31은 모서리 직전 구간이라 두 숫자를 그대로 이어 붙여 최적 자세 전환이라고 결론내리면 안 된다. 높이에 맞춰 구간·성과를 고르지 말고 아래 공통 정의로 재검토한다. Codex 제안을 유지해야 할 의무는 없다.

기존 산술 감사: 원자료 height_rel=root_z−terrain_z, 최대 오차 2.78e-17m. 서버 A048과 PC A048의 높이 차이는 초기 구간에도 남는다. 스캐너·지형의 동등성까지 검증된 것은 아니다.

## 4. 더 나은 분석 방법 — 정책 평균만 비교하지 말 것

### 4-1. 식별·계측 대응을 먼저 확인
- run/보상 전체/학습 seed/평가 seed/checkpoint iter/PC/평가기·registry·계측 코드 식별자를 표에 넣는다. 서버와 PC 결과는 별도 층으로 표시한다.
- 원 학습 report를 env·로그·checkpoint와 직접 대조해 REPORT_READ_STATUS를 기록한다. 기존 읽기 기록은 위치 안내이며 새로 읽었다고 허위 보고하지 않는다.
- height_rel뿐 아니라 같은 행의 root_z와 terrain_z를 함께 추출한다. 세계 z는 지형 origin이 달라 run 간 절대값으로 비교하지 말고 초기 지형/위치 기준 상대 변화도 표시한다.
- 서버·PC scanner 설정(패턴·범위·offset·좌표 정렬·mesh 경로·갱신 간격)과 지형 조건 차이를 확인한다. 불명확하면 cross-PC 관측은 유지하되 동일 계측 확정으로 쓰지 않는다.
- 첫 episode 종료 이전만 동작 분석에 사용. 종료/리셋 뒤 좌표를 연결하지 않는다. NaN·누락·upright 미측정은 별도 집계한다.

### 4-2. 상황별 구간과 성과를 고정
분석 전에 도구 주석과 보고서에 정의를 적는다. 기존 정의를 우선 재사용한다.

- **험지 전진·옆걸음:** 서로 분리. 초기 1~3초 높이를 노출 변수로, 이후 생존·추종을 결과로 읽는다. 초기 이미 무너진 개체는 별도 층으로 보존한다. 실패 직전 높이는 원인 예측이 아닌 과정 기술이다.
- **계단 10cm·15cm:** 별도 표. 초기 접근, 모서리 직전 −0.5~0초, 이후 0~1.5초를 구분한다. 모서리 표지는 기존 지형 상승 정의. 미도달 개체를 누락하지 않고 따로 센다. ≥2단, 전 구간 생존, 진행/완주 지표, 추종을 분리하고 ≥2단 뒤 낙상도 별도 표시한다.
- **복합 우회전:** 초기 높이·속도·각속도·기울기와 이후 낙상·추종. 좌회전은 대응 비교군. 원 steps의 기울기 크기로 안/바깥 기울기 방향을 추정하지 않는다. 방향은 해당 진단 채널이 있는 경우만 사용한다.
- **밀침:** +x/−x/+y/−y를 분리. 실제 push 시각·크기·적용 대상 기록을 읽고 직전 −1~0초 높이와 이후 낙상·회복 시간·추종을 연결한다. 이벤트 정보가 없으면 임의 시각을 추정하지 말고 기존 recovery 지표로 제한한다. 초기 높이를 '밀침 직전 높이'라고 바꾸지 않는다.
- 속도·높이·기울기는 같은 표본과 구간으로 계산. 요약 지표마다 단위·분모·누락 수를 명시한다. body frame 속도와 world frame 높이 미분을 섞어 같은 축으로 해석하지 않는다.

### 4-3. 추출할 표 — 먼저 CSV, 그다음 사람이 읽을 표
**표 A — run×case×seed:** 보상 전체 식별, 학습/평가 seed, 환경, 표본 수, 초기/사건 전 높이 중앙값·IQR, 속도/명령 오차, 기울기, 생존, 낙상, 계단 도달, 회복. 기존 표와 새 정의가 다른 이유를 설명한다.

**표 B — 같은 정책 내 성패:** 각 구간 높이를 결과별로 나눠 표본·중앙값·IQR를 제시. 성공 사례만 먼저 고른 높이를 최적이라고 선언하지 않는다. 생존+추종, 계단 도달+생존의 교차 분류를 보존한다.

**표 C — 높이 구간별 결과:** 결과를 보기 전에 0.02m 고정 폭을 기본으로 설정하고 표본 수와 함께 생존·추종·등반/회복을 표시한다. 구간 경계 민감도는 원점 0.01m 이동 또는 0.04m 폭으로 한 번만 대조한다. 공통 표본 지지가 없는 구간끼리 우열을 단정하지 않는다. 서버/PC와 정책별 표를 우선하며 합산표로 정책 효과를 숨기지 않는다. 희소 구간을 매끈한 곡선으로 메우지 않는다.

**표 D — 변수 변경→상태→성과:** 같은 기준에서 보상 한 항만 다른 쌍을 모아 '변수·전후 값 → 같은 구간 높이/속도/기울기 변화 → 각 시나리오 생존·추종 변화 → 지지/반례'를 나란히 표시한다. 보상 변경 효과와 높이의 인과효과는 구분한다.

**표 E — 최종 상태 목표:** 상황별 낮음 유리/높음 유리/중간 구간/단조관계 미확인, 최선 관측점, 유망 범위, 표본·정책·seed 수, 보존할 추종, 반례, 확신도. 수치가 정당화되지 않으면 범위 대신 우선 비교할 관측점을 선택하고 무엇이 부족한지 구체화한다.

가능하면 정책 내 비교와 정책 간 비교의 방향이 같은지 확인한다. 반대면 적용 범위를 좁힌다. 96개 env를 독립 학습 96회로 세지 않는다. 평가 seed별 결과를 분리하고 학습 run 수준 불확실성을 명시한다. 매끄러운 높이 곡선·전체 상관계수 하나로 최적점을 정하지 않는다.

## 5. 상태 목표에서 튜닝 정책으로 연결
순서는 **관측 → 실패 경로와 미설명 부분 → 강좌·배포의 방향 예측 → 시험 이력 대조 → 정책 선택**이다.

1. 시나리오별 최선의 상태 가설을 먼저 적고 동일 로봇에서 충돌하는지 본다. 공통 높이 하나가 맞는지, 상황별 자세 조절이 필요한지는 결론이지 전제가 아니다.
2. 기존 reward 중 무엇이 목표 상태에 직접/간접 영향을 주는지 구분한다. lin_vel_z는 수직 속도, flat_orientation은 수평 자세다. 둘을 높이 목표 항이라고 부르지 않는다.
3. 실제 단일변수 이력에서 그 방향이 목표 상태와 성능을 함께 움직였는지 대조한다. 상태만 좋아지고 추종/계단이 망가지면 반례를 우선순위에 반영한다.
4. 최종 비교표에는 현재 실패, 바꿀 행동, 기준 보상 설정, 변수·변경값, 강좌 예측, 지지/반대 관측, 보존 이득, 값/폭 이유, 같은 비용 대안, 결과별 다음 결정을 넣는다.
5. '미시험', '작은 변경', '범위 안', '자료가 늘어난다'만으로 값을 선택하지 않는다. 새 값이 정당화되면 책임 있게 한 안을 우선 선택한다. 부족하면 임의 최적값 대신 자료가 지지하는 최선 관측 설정과 남은 연결을 구분한다. 기존 실험의 반복을 새 후보처럼 제시하지 않는다.
6. 상황별 보상 분기·높이 목표 항 신설·커리큘럼 코드 변경이 필요하면 배포 가중치 수정 범위 밖으로 분리한다. 실행 가능한 정책과 장기 연구 아이디어를 섞지 않는다.
