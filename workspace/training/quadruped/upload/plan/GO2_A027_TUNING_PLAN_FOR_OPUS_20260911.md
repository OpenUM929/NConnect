## 4. 내 1순위 조건부 튜닝 가설

- **제안·추론:** 몸통 회전 각속도 벌점을 소폭 강화하여 하강 중 급격한 회전을 줄일 수 있는지 시험한다. A027이 이 인과관계를 입증했다는 뜻은 아니다.

- **왜 tracking을 다시 올리지 않는가:** 이미 G4/G6 손실과 paired 생존 후퇴가 있어 추종 보상 추가 강화보다 생존 약점 분리가 우선이다(E2).

- **과거 경고:** G-A016의 Pilot -0.05→-0.15 실험과 G-A024의 Default 실험을 동일 조건 재현으로 취급하지 않는다. 과거 붕괴 기록은 위험 신호이지 -0.06의 실패/성공 증명은 아니다. Opus는 해당 원시 evaluator·baseline 대응을 확인한 범위에서만 반론 근거로 사용한다(`config/experiments/G_A016_pilot_ang_vel_xy_m015.json`, 마스터 §18~19).
- **외부 근거:** 이번 안은 로컬 snapshot/실측에 기초한 가설이며 외부 문헌으로 정확한 값이나 효능을 정당화하지 않았다. Opus가 문헌을 추가하면 원문·함수·기체·적용 한계를 제시해야 한다.

## 6. 조기중단·시간 박스·회수

- 실행 전 로컬에서 배포 경로 무결성, 단일 reward diff, seed 적용, package SHA/CRC/manifest/CRLF/bash -n, 한 줄 명령, 완료표식·다운로드 경로를 준비한다. 준비 실패는 HOLD — package 미검증이며 서버를 켜서 준비하지 않는다.
- P1 첫 paired case에서 identity·시간축·자세 채널 오류가 있으면 중단·실패로그 회수. P2 수치 비유한/프로세스 오류 시 중단. 정상이라도1,000iter에서 종료하며 자동 연장하지 않는다.
- 학습 중500iter 부근은 **배포 저장주기에 실제 존재하는 가장 가까운 checkpoint**의 로그/무결성 확인 지점이다. 중간 평균 reward만으로 채택/기각하지 않으며 checkpoint를 만들려고 배포 코드를 바꾸지 않는다.
- 평가 초반 G5 하강을 우선 실행. 유효한 paired case의 생존 delta<-0.10이면 안전 조기중단; 부분 결과로 전체점수를 만들지 않는다. 마지막 정상 checkpoint와 실패 자료를 회수한다.
- 현재 GPU 잔량·확인 시각 **미측정**. P1/P2/P3를 한 세션에 묶어 약속하지 않는다. P1 상한은18case+18영상, P2 상한은1,000iter×2arm+138정량case+30영상; P3는 P2 성공 후 같은 상한으로 별도 승인한다.
- 벽시계 예산은 최신 서버 잔량 확인시각과 같은 환경의 로그/첫 실행 실측으로 계산: `T=학습2회+평가138case+영상30개+패키징·다운로드 실측+회수여유`. 병렬 실행을 가정해 나누지 않는다. 자료가 없으면 시간 숫자를 지어내지 않는다. 첫 case/영상 후 비용 재산정, **잔량 < 남은 실행추정+회수여유**면 다음 단위를 시작하지 않는다.
- 회수여유는 실제 ZIP 크기/다운로드 속도·포장시간에서 산정하고 완성된 필수물 로컬 검증 전 서버 종료 지시 금지. 현 단계 서버 명령 없음.
