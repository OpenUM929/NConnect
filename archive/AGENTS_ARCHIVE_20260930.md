## 자력 검증 우선 (260830 신설)

**로컬에서 확인할 수 있는 것을 사용자나 다른 배우에게 묻지 않는다.** 질문은 실측을 끝낸
뒤 남은 것만 한다. 근거 없이 올린 질문은 사용자의 시간을 쓰는 비용이며, 되물음 한 번이
곧 한 턴이다.

1. **묻기 전에 연다.** 저장소 안 파일·로그·코드 주석·해시·가중치로 답이 나오는 질문은
   질문이 아니라 미실행 작업이다. 판단·권한·대회 공지처럼 저장소 밖에만 있는 사실만
   질문 대상이다.
1-b. **역할 분담이 답을 결정하는 질문을 하지 않는다.** 이 프로젝트의 롤은
   **사용자가 실행하고 메인 루프가 지시·검증·기록한다**이다. 따라서 "우리가 그 단계를
   지시했는가"는 사용자에게 물을 것이 아니라 **「진행」 원장에서 유도할 것**이다.

   > **⚠️ 정정 (260830 · 팀장 판정 Q4 수용).** 이 항목의 초판은
   > *"지시가 없었으면 행위도 없다"* 라고 적었다. **너무 강한 명제였다.**
   > 원장이 확정하는 것은 **우리 쪽 행위(지시·검증·기록)**뿐이고,
   > **사용자 쪽 행위는 확정하지 못한다** — 사용자는 지시 없이도 행동할 수 있고 실제로 그랬다
   > (서버 파일 업로드). F44를 「공식 제출 0회」로 단정한 것이 이 오류의 실증이며,
   > 올바른 표기는 **「원장상 업로드 지시 0건 · 실제 제출 여부 [미측정]」** 이다.
   >
   > **경계: 원장으로 유도할 수 있는 것 / 없는 것**
   > - 유도 가능 — 우리가 무엇을 지시했나, 무엇을 검증했나, 어떤 산출물이 언제 생겼나
   > - 유도 불가 — 사용자가 외부 시스템(대시보드·강좌 사이트)에서 무엇을 했나
   >
   > 후자는 `[미측정]`으로 두고 **회수 방법과 함께** 올린다. 단정도, 방치도 하지 않는다.
2. **자기 로그를 먼저 읽는다.** 외부 문서를 추정하기 전에 우리가 남긴 실행 로그를 grep한다.
   실증 — `F26`(학습=제출)은 2일간 캠페인 예산의 전제였는데, 반증이 우리 로그
   `reports/train_260828-02.log:111247`에 처음부터 찍혀 있었다:
   *"⚠️ 이것은 **예선 제출이 아닙니다** — 제출은 대회 웹사이트에서 policy.pt 를 직접 업로드하세요."*
3. **해시 불일치는 내용 불일치의 증거가 아니다.** 직렬화가 비결정적일 수 있다.
   실증 — `exported/policy.pt`는 같은 checkpoint에서 export해도 파일 해시가 매번 다르지만
   (4종 관측) 가중치는 동일하다. **동일성 판정은 가중치 비교로 한다**
   (`torch.jit.load(...).state_dict()` 텐서 대조). 해시는 무손상 증거로만 쓴다.
4. **식별자는 재현 가능한 것으로 적는다.** 문서에 정책을 특정할 때 비결정적 해시 대신
   `checkpoint의 iter + model_best.pt sha256`을 쓴다.
5. **질문은 근거와 함께 만든다.** 외부 배우에게 넘길 때는 이미 확정한 사실·재현 명령·
   판정 가능한 질문형을 함께 싣는다(REV_GUIDE §6-b·§6-d). "어떻게 할까요"는 질문이 아니다.

## 계획 우선·결정 즉시 기록 (260830 신설)

**전제가 바뀌면 명령이 아니라 계획을 먼저 낸다.** 260830에 전제 3개가 동시에 무너졌는데
(F26 자동제출 오독 · F44 제출 0회 · D23 H1 전용 확정) 메인 루프는 계획 재작성 없이
학습 명령 한 줄로 넘어갔다. 사용자가 세 번 연속 지적해야 멈췄다.

1. **사용자의 범위·기체·일정 결정은 발화 즉시 `CAMPAIGN_SCHEDULE.md`와
   `PROJECT_STATE.md` 결정표에 행으로 남긴다.** 실증: "2족만 한다"가 어느 원장에도 없어
   메인 루프가 Go2 착수를 3턴 반복 제안했다(D23). 기억이 아니라 원장이 정본이다.
2. **단발 명령으로 계획 변경을 대신하지 않는다.** 전제가 바뀌면 ① 무엇이 무너졌는지
   ② 남은 점수축과 각 축의 통제 가능 여부 ③ 새 단계표 ④ 그제서야 첫 명령, 순으로 낸다.
3. **새 학습을 제안하기 전에 기존 판정과 대조한다.** 실증: `track_ang_vel_z_exp` 인상안은
   D18이 "선속도 우세(Run 05)가 회전 우세(Run 04)보다 가중 +6.78 낫다"고 판정한 시소를
   **거꾸로 미는 것**이었다. 자기 판정을 조회하지 않은 제안은 제안이 아니다.
4. **통제 가능한 축을 통제 불가능한 축보다 먼저 쓴다.** 시뮬 70점은 운영진만 채점하므로
   우리 실험은 blind bet이지만, 의도분석 20 + 리포트 10은 우리가 직접 검증·확정할 수 있다.
   같은 시간이면 확정 이득이 blind 이득에 우선한다.
5. **판정 요청의 선지는 원장 원문과 대조한 뒤 만든다.** 판정자는 선지 밖을 볼 수 없으므로
   **틀린 선지는 반드시 틀린 판정을 낳는다.** 원칙 12(피측정자가 자를 소유하지 않는다)의
   역방향 위반 — 질문자가 선지를 만들어 판정을 유도하는 것 — 을 막는다.
   실증(260830): 팀장에게 낸 `Q3. (b) ▲ blocked — 공백 C(마감일) 미회수`는 메인 루프의 창작이었다.
   원장 원문(`PROJECT_STATE.md:871`)이 막은 것은 **① iter 상한** ② **공백 F**(50시간 해석)인데
   이를 **① 학습 시작 자체** ② **공백 C**(마감일)로 두 번 변형해 선지에 넣었다.
   팀장은 주어진 선지 중 골랐을 뿐이고 D28이 나왔다. 선지를 만들기 전에 **인용할 원문 줄을 연다.**
6. **단계표에는 「등급」이 있어야 한다 — `필수(제출요건)` / `개선` / `조사`.**
   **`필수` 행은 `blocked` 상태를 가질 수 없다.** 막히면 일정 조정이 아니라 **제출 불가**이므로
   `▲ 제출 불가 — 즉시 해소 대상`으로 격상한다. 등급이 없으면 제출 요건과 개선 작업이
   같은 형식으로 나란히 놓여 **둘 다 미룰 수 있는 것처럼 보인다**(실증: B2 = 제출 체크리스트 #3).
7. **벽시계 작업을 사람 시간 입력으로 막지 않는다.** 학습은 tmux로 걸어두면 사람 시간을 쓰지 않는다.
   달력·일정 미확인을 이유로 GPU 작업 착수를 막는 것은 두 예산의 혼용이며, 오히려
   **학습이 도는 동안 문서 축 작업을 병렬 배치**하는 것이 정본이 명령하는 동작이다
   (`prelim-campaign-manager.md` L91-96·L101).

## 제출 전 자체 70점 게이트 (260831 신설)

1. 자체 채점은 `시뮬레이션 proxy /70`, `설계 의도 자체감사 /20`, `리포트 자체감사 /10`,
   `총 자체예상 /100`을 별도 표시한다. 운영진 점수처럼 쓰지 않는다.
2. 공개된 공식 개념은 `survival_rate × tracking_score`까지이며 tracking의 정확한 변환식은
   비공개다. 따라서 내부식은 버전·근거·한계를 고정한다. 현재 v1은 Run06 `env.yaml`의
   `std=0.5`와 exponential tracking 형태를 사용한
   `tracking_proxy = exp(-(RMSE/0.5)^2)`이고, 좌우·회전·경사 쌍은 더 나쁜 방향을 채택한다.
3. 시나리오 내부 통과 기준은 `survival_proxy ≥ 0.95`와 `tracking_proxy ≥ 0.70`을 동시에
   만족하는 것이다. H1~H7 전부 측정되고 모든 시나리오가 이 기준을 통과하며 가중 시뮬
   proxy가 0.70 이상일 때만 `SELF_ASSESSMENT_PASS`를 쓴다.
4. 최종 제출 후보 승급은 **총 자체예상 70점 이상**을 최소조건으로 하고, evaluator 불확실성
   여유를 위해 목표는 75점 이상으로 둔다. 문서 30점은 파일 일치·근거 완결성 rubric을 실제로
   감사한 만큼만 더하며, 단순 파일 존재만으로 만점을 주지 않는다.
5. `SELF_ASSESSMENT_PASS`는 공식 합격이 아니다. 그러나 `INCOMPLETE`, 시나리오 FAIL 또는
   총 자체예상 70점 미만인 정책은 공식 제출로 약점을 확인하려 하지 말고 먼저 평가·튜닝한다.

## 튜닝 근거 선행·반복 질문 방지 (260831 신설)

사용자가 보상값의 이유, 현재 만족 여부, 학습 지속 이유를 다시 물어야 했다면 보고 실패다.
H1 학습·튜닝·평가 답변과 실행계획은 다음 규칙을 의무 적용한다.

1. **항상 `H1_REWARD_EVIDENCE_MASTER.md`를 먼저 읽는다.** 새 artifact가 이 문서보다 최신이면 artifact를 우선하고 같은 턴에 마스터를 갱신한다. 과거 계획의 `완료`, `PASS`, `최종 후보`가 최신 실험 감사와 충돌하면 최신 근거로 즉시 철회·재분류한다.
2. **값의 출처와 값의 성능을 분리한다.** 배포 기본값·코드 권장범위·Isaac Lab upstream 값은 후보 출발 근거일 뿐 NCRC 최적값이나 만족 판정이 아니다.
3. **모든 reward를 `만족 / 부분 만족 / 미만족 / 미측정 / INCONCLUSIVE` 중 하나로 표시한다.** 각 행에 로컬 `파일:줄` 또는 artifact, 외부 공식문서/논문, 적용 한계, H1~H7 직접 측정 범위를 붙인다.
4. **5,000 iter 초과 학습 전에 8개 항목을 제시한다.** 현재 단계, 단일 변경, 통제 변수, 로컬 근거, 외부 근거, H1~H7 측정범위, 사전 판정 기준, seed/evaluator 반복과 안전 중단·회수점이다. 하나라도 없으면 `HOLD — 근거 불충분`이다.
5. **단일 seed·단일 rollout·평균 reward로 최적·수렴·확정 만족을 선언하지 않는다.** promising candidate는 원칙적으로 독립 seed 반복과 동일 evaluator를 거친다. 예산 때문에 못 하면 `exploratory` 또는 `PARTIAL`로만 기록한다.
6. **학습 중단/지속 판단에는 정보가치와 회수 안전성을 함께 쓴다.** 현재 iteration, 가장 가까운 보존 checkpoint, 중단 시 잃는 가설, bundle 완성 조건을 먼저 확인하고 명령을 낸다.
7. 사용자 첫 화면에 **왜 지금 이 작업을 하는지**, **무엇이 만족/미만족/미측정인지**, **결과가 어느 의사결정을 바꾸는지**를 마스터 링크와 함께 표시한다.

## 학습 report 필독·원인 우선 연구 계약 (2026-09-13 사용자 결정)

H1·Go2 튜닝 기획·평가·보고를 수행하는 메인과 모든 서브에이전트에 적용한다.
보고서 존재 확인이나 다른 배우의 요약만으로 읽었다고 하지 않는다.

1. **튜닝 후보 선정 전에 해당 정책과 대조군의 학습 `report.html` 본문을 직접 읽는다.**
   학습 run·checkpoint iter/model SHA·env reward snapshot·학습 로그와 대응을 확인한다.
   파일명/수정시각/같은 폴더만으로 대응을 확정하지 않는다. export 해시 차이는 tensor 의미 차이로 단정하지 않는다.
2. `REPORT_READ_STATUS=READ_MATCHED|READ_UNMATCHED|MISSING|NOT_APPLICABLE`를 출력한다.
   읽은 경로·보고서의 학습시각/iter/보상값·대조한 로그와 정책 식별자·일치/불일치·미확인 근거를 남긴다.
   `READ_MATCHED`는 대응 확인이지 성능 판정이 아니다.
3. 학습 HTML, 내부 `SELF_EVAL_REPORT`, 기술 개선 제출문은 서로 다른 자료다.
   평가 전용 run은 새 학습 HTML이 없을 수 있으나, 튜닝에 쓰는 정책의 원 학습 report 조회를 생략하지 않는다.
   `NOT_APPLICABLE`은 정책을 생성하지 않은 도구 smoke 등 실제 비해당 사유를 적을 때만 사용한다.
4. report 누락/오래된 파일/정책 대응 불명은 `REPORT_REQUIRED_NOT_ACQUIRED` 또는
   `REPORT_POLICY_UNMATCHED`로 기록한다. 먼저 로컬 원 학습 bundle·보존 snapshot·로그를 검색한다.
   그래도 없으면 회수/복구 방법을 기록한다. 추정 HTML을 원본인 것처럼 만들지 않는다.
   **[2026-09-14 개정] 휘발 서버에서 이미 사라진 과거 run의 report는 `REPORT_REQUIRED_NOT_ACQUIRED — 복구 불가`로
   한 번 기록하고, 같은 run의 원 학습 로그 요약값(최고 reward·terrain level·학습 낙상률·action std)과
   SELF_EVAL을 대체 근거로 삼아 진행한다. 이 상태는 새 reward 후보 확정·새 학습 패키지 발행을 막지 않는다.**
   막히는 것은 새 run의 회수 완결 판정(§7)뿐이다. 같은 archive를 재검색하거나 원본 제공을 반복 요청하지 않는다.
   (구판 차단 문구는 `SUPERSEDED` — 루트 「튜닝 요청 산출물 계약」 참조.)
5. 연구 순서는 **학습 report·env·로그 대응 → 내부 시나리오 평가 → 영상/telemetry로 실패 유형 구분
   → 경쟁 가설 비교 → 근거 있는 단일변수 후보 → 대조 실험·독립 seed**다.
   HTML의 안정/공격 설명과 일반 경고는 가설 단서일 뿐 인과효과·최적 가중치 근거가 아니다.
6. 학습낙상률/terrain level/mean reward를 시나리오 survival/tracking 또는 공식 점수로 바꾸지 않는다.
   보고서 수치의 집계 구간과 지표 출처를 확인하고, 충돌은 원 로그와 evaluator 조건으로 해소한다.
7. 새 학습 회수에는 같은 run의 `report.html`과 로그·env·checkpoint 대응 자료를 결과 bundle 및 SHA 목록에 포함한다.
   누락하면 해당 공백을 기록하며 다운로드 완결 또는 튜닝 근거 완결로 보고하지 않는다.
8. 최신 지침은 역할 문서의 과거 다음 실행·고정 현재단계보다 우선한다. H1/Go2 캠페인은 분리한다.
